JIRA-AI — 이슈 자동 분석·업무 자동화 서비스

Jira에 문의가 들어오면 담당자가 문서를 뒤지고, 소스를 열고, 예전에 비슷한 이슈가 있었는지 찾습니다. 이 앞부분을 AI가 먼저 해 두면 어떨까에서 시작했습니다. 메일 도메인 구축처럼 매번 똑같이 반복되는 요청은 담당자가 승인만 하면 처리되게 했습니다.

무엇이 되게 했나

Java 17 · Spring Boot · LangGraph4j 1.7 · Spring AI · Azure OpenAI · Kafka · Redis · MariaDB/Flyway · React 18 + TypeScript

커밋 2026.04 ~ 2026.09 · 937건 (원격에서 다시 확인한 건 904건)
사내 단독 개발

모든 분석은 비슷한 이슈, 사내 지식, GitLab 소스를 먼저 모은 뒤에 답을 씁니다. 근거가 모자란 답은 다시 조사한 뒤에도 통과하지 못합니다. 검증되지 않은 지식은 검색에 섞이지 않고, 실패한 분석은 60분 뒤 다시 처리됩니다. 토큰 없는 요청은 401, 권한 없는 요청은 403이고 이건 테스트로 고정했습니다. 외부 시스템에 등록하는 작업은 담당자 승인과 예약 시점 재확인 없이는 실행되지 않습니다.

아직 못 한 것도 있습니다. 답이 얼마나 정확해졌는지, 담당자가 얼마나 시간을 아꼈는지는 재지 못했습니다. 그래서 숫자는 적지 않았습니다.

설계할 때 정한 원칙은 단순합니다. 항상 필요한 조회는 LLM에게 맡기지 않고 그냥 실행합니다. 실패하면 바로 재시도하지 않고 보관했다가 나중에 처리합니다. 지식이든 등록이든 패치든, 밖으로 나가는 건 사람 승인을 한 번 거칩니다. 정확도 평가 데이터셋, exactly-once, parser 기반 패치 검증은 뒤로 미뤘습니다.

LangGraph4j 15노드 조건부 워크플로

2026.04 ~ · 3노드에서 15노드까지

배경처음엔 LLM을 한 번 부르고 끝이었습니다. 이슈마다 난이도가 달라서 어떤 건 근거를 더 찾아야 했고 어떤 건 답을 다시 검수해야 했는데, 한 번 호출로는 그걸 통제할 수 없었습니다.

수행agent, tools, parse_result 세 노드 루프로 시작했습니다. 그 위에 수집과 검수 서브그래프를 얹고, 설정에 따라 MCP 도구를 먼저 부르는 단계를 붙여 15노드까지 늘렸습니다. 비슷한 이슈 조회는 LLM에게 맡기면 가끔 건너뛰어서, 항상 실행되는 단계로 뺐습니다.

성과아래 그림의 분기가 기준일 코드에 그대로 있습니다. addNode 15개를 직접 세어 확인했습니다.

한계초기 커밋에는 synthesis에서 review로 가는 edge가 빠져 있었고 다음 커밋에서 이었습니다. 정확도가 얼마나 좋아졌는지는 재지 못했습니다.

GitLab 소스 → RAG 코드 인덱스 자동 생성

2026.07 ~ 08

배경소스 전체를 프롬프트에 넣을 수는 없었습니다. 그리고 LLM은 없는 파일 경로를 그럴듯하게 지어냅니다.

수행허용 확장자만 고르고 build, dist, generated, test 폴더는 뺍니다. 후보를 500개까지 모으고 그중 30개를 고르게 하되, LLM이 고른 경로는 원래 후보 목록에 실제로 있는지 다시 확인합니다. 파일은 30,000자, 전체는 100,000자에서 자릅니다. 이미 인덱스가 있으면 덮어쓰지 않고, 여러 모듈 요청은 한 줄로 세워 처리합니다. 나중에 지식 문서(module/)와 코드 인덱스(gitlab/) 폴더를 나눴고, 옛 경로는 폴백으로 남겼습니다.

성과없는 경로가 답에 섞이는 일을 구조로 막았습니다. 폴더를 옮기는 중에도 검색이 깨지지 않는 걸 테스트 7개로 확인했습니다.

한계만들어진 인덱스가 얼마나 정확한지, 토큰이 얼마나 줄었는지는 재지 못했습니다. Milvus도 붙여 봤는데 서버를 세우지 못해 걷어냈고, 지금은 파일 기반 RAG입니다.

담당자 지식의 승인 대기 격리

2026.07

배경담당자가 단 해결 답변을 지식으로 쌓고 싶었습니다. 그런데 검증되지 않은 지식이 다음 답변의 근거가 되면 틀린 게 그대로 굳습니다.

수행처음 버전은 "검색 반영 전"이라고 안내하면서 실제로는 읽힐 수 있는 폴더에 저장하고 있었습니다. 그걸 발견하고 _pending 폴더로 옮겼습니다. 관리자가 검토해서 정상 경로로 옮겨야 검색에 잡히고, 프로젝트 필터가 _pending을 걸러내는 걸 테스트로 고정했습니다.

성과승인 전 지식은 검색에서 보이지 않습니다.

한계관리자가 실제로 승인 이동을 얼마나 했는지는 운영 기록이 없습니다.

장시간 파이프라인 실패의 DLT 보존과 지연 재접수

2026.07

배경분석 하나가 수십 초 걸립니다. 실패하면 1초, 2초, 4초 뒤에 다시 시도하는데, 같은 이유로 또 실패하고 비용만 들었습니다.

수행파이프라인 실패는 재시도 대상에서 빼고 바로 DLT로 보냅니다. 스케줄러가 60분 지난 메시지를 꺼내 retryCount를 하나 올려 원래 토픽에 다시 넣고, 그 다음에 offset을 커밋합니다. consumer group을 고정해서 다음 tick에 이어서 읽습니다.

성과실패를 잃어버리지 않고 나중에 다시 처리합니다. retryCount가 올라가는 건 테스트로 확인했습니다.

한계재발행 뒤 커밋 전에 죽으면 중복이 생길 수 있습니다. at-least-once이고, 그래서 exactly-once라고 말하지 않습니다. DLT 파티션이 하나고 시간 순서를 가정합니다.

인증·SSO·테넌트 경계

2026.07 ~ 09

배경API가 permit-all이었습니다. 대시보드에서는 Axios 요청과 SSE가 동시에 401을 받으면 회전형 refresh token을 둘이 같이 써서 한쪽이 무효가 됐습니다.

수행JWT 필터를 넣고 ADMIN, OPERATOR, VIEWER 경로 규칙을 만들었습니다. 필터가 두 번 실행되지 않게 servlet 자동 등록도 껐습니다. 토큰 갱신은 공유 Promise 하나로 묶어 동시에 401이 와도 한 번만 갱신합니다. A10 SSO는 Redis에 10분짜리 nonce를 두고 cookie state를 상수 시간으로 비교한 뒤 한 번만 소비하고, 허용된 그룹만 가입시킵니다. 사용자 키도 (group_seq, login_id) 복합 키로 바꿨습니다.

성과토큰이 없으면 401, VIEWER가 ADMIN 경로를 치면 403, OPERATOR가 실행하면 200. 테스트로 고정했습니다.

한계운영 SSO 로그인이 실제로 됐는지, 키 관리와 침투 테스트는 이 커밋으로 말할 수 없습니다. single-flight는 같은 탭 안에서만 통합니다.

메일 도메인 구축 자동화 — 사람 승인 + 외부 상태 재확인

2026.08 · 90개 파일 · V43 migration

배경구축 요청은 계속 들어오는데 사람이 처리하다 빠뜨리는 일이 있었습니다. 그렇다고 A10과 WBlock에 쓰는 작업을 무조건 자동으로 돌리는 건 위험했습니다.

수행접수, 승인 대기, 예약, 사전 점검, 등록, 그리고 완료, 취소, 수동검토, 실패 상태를 만들었습니다. webhook에 찍힌 사람을 믿지 않고 Jira를 다시 조회해 실제 작성자와 담당자를 비교합니다. 예약 시점에 이슈 fingerprint와 취소 여부를 다시 보고, 사전 점검과 write_enabled를 통과해야 씁니다.

성과접수부터 등록, 보상까지 한 흐름으로 이어집니다. 오래 멈춘 작업은 회수하고, 시도 상한을 넘거나 보상 삭제가 실패하면 사람 검토로 넘깁니다.

한계등록 성공률과 처리량은 아직 숫자로 없습니다. 이 커밋 뒤로 중복 라우팅, rollback, rate limit을 고치는 커밋이 이어졌습니다.

AI 패치의 정적 검증 게이트와 쓰기 connector (source-fix)

2026.07 · 별도 로컬 lineage

배경LLM이 만든 패치를 그대로 쓰는 건 위험했습니다. GitLab에 쓰다 실패한 게 조용히 묻히면 더 위험했습니다.

수행보고서의 Before/After를 짝지어 원문과 정확히 맞는지 먼저 보고, 안 맞으면 줄 단위 공백 차이만 허용합니다. 문자열과 주석을 감안해 괄호 균형을 세고, After에만 새로 생긴 식별자를 뽑아냅니다. 전부 순수 함수고 테스트가 붙어 있습니다. GitLab에 branch, commit, MR을 만드는 connector도 만들었는데, 처음엔 모든 예외를 "없는 브랜치"로 삼켰습니다. 7분 뒤 커밋에서 404만 그렇게 처리하고 나머지는 올리도록 고쳤습니다. 재기동하면 미완료 작업을 다시 발행하고, Redis lock(15분)으로 중복 실행을 막습니다.

성과실패가 조용히 묻히지 않습니다.

한계parser가 아니라 휴리스틱입니다. 컴파일이 되는지, 의미가 보존되는지는 보장하지 않습니다. 이 저장소는 remote가 없어서 배포 여부도 말할 수 없습니다.

이 항목 커밋 937건 중 428건에 Claude 계열 공동 저자 트레일러가 있습니다. 제가 한 일은 문제를 정하고, 승인과 재확인과 상한을 어디에 둘지 정하고, 결함을 찾아 다시 검수하고, 테스트로 경계를 고정하는 것이었습니다. 코드를 한 줄씩 다 손으로 친 건 아닙니다.

02 · Workflow Engine

IssueFlow — 범용 워크플로 엔진

JIRA-AI를 만들면서 도구나 시나리오가 늘 때마다 코드를 더 쓰는 게 싫어졌습니다. 노드 그래프를 정의하면 Jira 조회, 조건 분기, MCP 도구가 조합돼 실행되고, 승인과 예약과 비밀은 엔진이 챙기는 것을 목표로 만들고 있습니다.

Java 17 · Spring Boot · PostgreSQL/Flyway · MCP · React 18 + @xyflow/react

커밋 2026.09 · 로컬 전용 94건 (baseline, snapshot, 분할 커밋 포함)
로컬 개발 단계

Jira 이슈 하나가 저장된 워크플로를 API에서 저장소까지 끝까지 통과합니다. 쓰기 도구는 기본이 dry-run이고 실제 실행은 원장을 거치는데, 이건 테스트로 확인했습니다. step, 시간, AI 호출, token, cost 상한을 넘으면 멈춥니다(노드 경계에서 검사해서 최대 N-1회는 넘어갈 수 있습니다). 비밀은 정의 JSON에 평문으로 남지 않고, 승인은 링크 미리보기(GET)만으로는 되지 않습니다.

도구마다 노드를 만들지 않고, 서버가 tools/list로 알려주는 목록을 읽는 mcp.tool 노드 하나로 통일했습니다. 서버가 readOnlyHint를 주지 않으면 쓰기로 봅니다. 첫 슬라이스는 AI 합성 없이 조회, 파싱, 분기, 기록만으로 먼저 뚫고 검증 단계를 나중에 붙였습니다. 원격 반영과 배포, 외부 MCP 서버와의 상호운용 테스트, 옛 secret 일괄 재암호화는 아직 안 했습니다. 시나리오 하나 추가하는 데 얼마나 걸리는지도 아직 재지 못했습니다.

엔진, 보안, 승인에서 확인한 것

2026.09

수행WorkflowEngine에 대기 후 재개, node retry, step과 시간과 반복과 AI 호출과 token과 cost 상한, 진행 이벤트를 넣었고 테스트 13개가 같이 들어갔습니다. SecretBox와 CredentialStore는 32바이트 외부 키로 AES-GCM 저장을 하고 마스킹과 audit를 남깁니다. WorkflowValidator는 schema, 노드 버전, 필수 입력, credential, 순환, cost를 검사하고 draft/publish/archive 이력을 남깁니다. 승인은 서명된 POST와 DB claim으로 중복 재개를 거절합니다. timer store, sweeper, schedule node도 있습니다.

성과재검수하면서 설정 API 필드 불일치, webhook 토큰 평문 저장, 정적 드롭다운, 근거 없이 100점 통과되는 결함을 찾아 실행 경계에서 고쳤습니다.

한계AI budget은 노드 경계에서 검사해 최대 N-1회 넘어갈 수 있고, reranker 호출 일부는 세지 않습니다. timer 제출이 실패하면 로그만 남고 FIRED 항목을 자동으로 다시 시도하지 않습니다. MCP 응답을 한 번에 읽어서 연결을 안 닫는 SSE 서버를 만나면 timeout까지 기다립니다.
