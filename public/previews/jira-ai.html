구간 03 — 근거 수집

아는 척하지 않도록 설계했습니다

답변을 쓰기 전에 시스템은 먼저 찾아봅니다. 사내 설계 문서와 매뉴얼, 같은 증상의 과거 이슈, 그리고 필요하면 실제 소스 코드와 운영 로그까지 — 모두 답변의 각주가 됩니다.

문서 검색은 키워드 매칭과 임베딩 유사도를 합산하는 하이브리드 방식입니다. 모듈별 README에서 키워드를 재추출해 검색어를 넓히고, 코드 인덱스 문서는 별도 트랙으로 관리합니다.

코드가 의심되면 계층을 따라 내려갑니다. 화면에서 시작해 SQL까지, 한 층씩 원인을 추적하고 그 결과를 원인 유형(SOURCE / LOGIC / CONFIG / DATA)으로 분류한 보고서를 남깁니다.

DEEP TRACING — 코드 계층 추적
Front→Controller→Service→Mapper→SQL

GitLab 코드 검색 + Loki 운영 로그 + 코드 인덱스 문서를 교차하며 최대 5회 반복 추적합니다.

📄RAG 설계 문서 searchDesignDocs모듈별 md 설계문서·매뉴얼 — 키워드+임베딩 하이브리드 검색
🗂️과거 Jira 이슈 searchJiraIssues · getIssueDetail같은 증상을 이미 해결한 이슈를 JQL로 찾아 근거로 인용
🧬GitLab 소스 코드 searchGitLabFiles · getGitLabFileContent모듈↔프로젝트 매핑을 따라 실제 코드를 열어 확인
📈Loki 운영 로그고객사·모듈별 레이블로 실제 에러 로그를 조회 (SaaS 멀티테넌시 매핑)
🌐네트워크 진단 lookupDns · testSslCertificate …DNS/PTR/포트/SSL/아웃룩 연동을 직접 점검해 메일 장애를 판별
✉️스팸 장비 searchSpamMailHistory …차단 이력 조회부터 재발송·예외 허용까지 — 결과가 확실하면 그래프를 통째로 우회
🖼️첨부 파일스크린샷은 Vision으로, 메일 파일(.msg)·이미지는 파서·OCR로 읽어 본문과 함께 분석

도구는 @McpModule + @Tool 애노테이션만 붙이면 자동 등록되며, 모듈별 활성 도구·선제/후천 호출 여부는 모두 DB 설정이라 재시작 없이 바뀝니다. 현재 활성 도구 14종.

구간 04 — 신뢰 엔지니어링

환각은 프롬프트가 아니라 시스템으로 막습니다

"AI를 믿지 말 것"이 이 시스템의 설계 전제입니다. 겸손은 상수로 박혀 있습니다.

MAX_REVIEW_COUNT = 3

스스로 검수하고 교정

게시 전 review 노드가 답변을 검수하고, 문제가 있으면 합성을 다시 시킵니다. 최대 3회 — 무한 고민은 없습니다.

McpAnswerCleaner

허위 섹션 삭제

도구를 실제로 호출하지 않았는데 LLM이 "조회 결과" 섹션을 지어내면, 그 섹션을 통째로 제거합니다.

INSUFFICIENT_INFO

모르면 반려

본문이 부실해 근거를 만들 수 없으면 답을 지어내는 대신 필요한 정보를 물어보며 정중히 반려합니다.

empty_rules = DENY

화이트리스트 필터

운영자가 필터 규칙으로 등록한 프로젝트·모듈만 분석합니다. 등록되지 않은 이슈는 AI가 손대지 않습니다.

G3: 사용례 0건 → 거부

패치 환각 검증

AI가 만든 코드 패치의 새 식별자를 GitLab 전체에서 교차 검색해, 사용례가 없으면 환각으로 보고 폐기합니다.

Semaphore(5)

동시 처리 제한

Jira 서버를 밀어붙이지 않도록 동시 분석을 5건으로 제한하고, API 호출 간 딜레이를 둡니다.

DLT + retry

실패를 삼키지 않음

분석 실패는 데드레터 토픽에 적재해 이력으로 남기고, 1시간 뒤 재접수합니다. 조용히 사라지는 이슈는 없습니다.

CircuitBreaker

외부 장애 격리

Jira·GitLab·LLM 등 외부 연동은 서킷브레이커로 보호되고, 차단 중의 실패도 분석 이력에 기록됩니다.

구간 07 — 자가학습 루프

쓸수록 똑똑해지고, 안 쓰면 잊습니다

답변의 끝은 폐기가 아니라 환류입니다. 성공한 답변과 사람의 해결책이 패턴 지식으로 쌓이고, 오래 안 쓰인 지식은 스스로 퇴역합니다.

CASE AAI가 성공하면, 그 답이 패턴이 됩니다

분석에 성공한 답변은 학습 이벤트로 발행되어 패턴 지식에 자동 등록됩니다.

CASE B사람이 해결하면, 그 해결책을 배웁니다

이슈가 Done으로 전환되면 담당자의 해결 내용을 학습합니다. 이때는 분석 없이 학습만 수행합니다.

TIER다음 이슈부터 바로 씁니다

새 이슈는 제목 10 · 본문 70 · 모듈 10 · 유형 5 · 제품 5점 가중치로 패턴과 대조되어, ≥90 즉답 / ≥70 검토 요청 딱지와 함께 답합니다.

DECAY안 쓰는 지식은 퇴역시킵니다

12개월간 적중 없으면 우선순위 -10, "도움 안됨" 피드백은 -20. 임계 이하로 내려간 패턴은 비활성화됩니다.

승인제사람이 최종 게이트입니다

자동 등록된 패턴은 대시보드 "검토 대기" 탭에서 운영자가 승인·거부하고, !지식저장 문서의 검색 반영도 승인 후 이뤄집니다.

FOR USERS — 문의 · 상담 · 설계

이슈를 쓰면, 나머지는 노선이 알아서

  1. 이슈를 등록합니다. 모듈을 정확히 고르고 증상·화면·시점을 구체적으로 쓸수록 답이 좋아집니다. 스크린샷 첨부도 AI가 읽습니다.
  2. 잠시 뒤 AI 댓글이 달립니다. 기본 15분 지연 후 분석이 시작됩니다(스팸 문의는 10초). 원인 · 안내 · 근거 링크가 함께 옵니다.
  3. 피드백을 남깁니다. 👍 도움됨 / 👎 도움 안됨 — 이 한 번의 클릭이 다음 답변의 품질을 바꿉니다.
  4. 필요하면 커맨드로 시킵니다. 정보 보강 후 !재분석, 해결 답변을 지식으로 남기려면 !지식저장.
FOR OPERATORS · DEVELOPERS

새 모듈을 노선에 올리는 법

  1. 필터 규칙부터 등록합니다. 화이트리스트 방식이라 필터 규칙에 없는 프로젝트·모듈은 AI가 분석하지 않습니다.
  2. 모듈 온보딩 마법사를 따라갑니다. GitLab 프로젝트 매핑과 RAG 문서 업로드까지 단계별로 안내합니다.
  3. 모듈 프롬프트와 MCP 호출을 설정합니다. 선제(Prefetch)/후천(Postfetch) 도구 호출은 DB 설정 — 재시작이 필요 없습니다.
  4. 패턴 "검토 대기"를 주기적으로 승인합니다. 자가학습이 쌓은 후보를 사람이 최종 판정합니다.
  5. 도구가 부족하면 직접 만듭니다. @McpModule + @Tool 두 애노테이션이면 자동 등록됩니다.
