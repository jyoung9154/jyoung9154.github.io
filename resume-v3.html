LangGraph4j 15노드 조건부 워크플로

아키텍처 · 2026.04 ~

배경처음엔 LLM을 한 번 부르고 끝이었습니다. 이슈마다 난이도가 달라서 어떤 건 근거를 더 찾아야 했고 어떤 건 답을 다시 검수해야 했는데, 한 번 호출로는 그걸 통제할 수 없었습니다.

수행agent, tools, parse_result 세 노드 루프로 시작해 수집과 검수 서브그래프, 설정 기반 MCP 호출을 붙여 15노드까지 늘렸습니다. 비슷한 이슈 조회는 LLM에게 맡기지 않고 항상 실행되는 단계로 뺐습니다. 맡겨 두면 가끔 건너뛰었기 때문입니다.

성과근거가 모자라면 다시 수집하고, 검수에서 떨어지면 다시 합성하고, 근거 부족으로 반려되면 코드 보고 단계로 한 번 되돌아갑니다. 되돌아가는 횟수에는 상한이 있습니다.

한계정확도가 얼마나 좋아졌는지는 아직 재지 못했습니다. 초기 커밋에서 빠뜨린 검수 edge는 다음 커밋에서 이었습니다.

GitLab 소스 → RAG 코드 인덱스 자동 생성

핵심 기능 · 2026.07 ~ 08

배경소스 전체를 프롬프트에 넣을 수는 없었습니다. 그리고 LLM은 없는 파일 경로를 그럴듯하게 지어냅니다.

수행허용 확장자만 고르고 build, dist, test 폴더는 빼고, 후보 500개에서 30개를 고르게 했습니다. LLM이 고른 경로는 원래 후보 목록에 실제로 있는지 다시 확인합니다. 지식 문서와 코드 인덱스는 폴더를 나눴고, 옛 경로는 폴백으로 남겼습니다.

성과없는 경로가 답에 섞이는 일을 구조로 막았습니다. 폴더를 옮기는 중에도 검색이 깨지지 않는 걸 테스트로 확인했습니다.

한계만들어진 인덱스가 얼마나 정확한지는 재지 못했습니다. Milvus도 붙여 봤는데 서버를 세우지 못해 걷어냈고, 지금은 파일 기반 RAG입니다.

성과처음 버전은 "검색 반영 전"이라고 안내하면서 실제로는 읽힐 수 있는 경로에 저장하고 있었습니다. 그걸 발견하고 고쳤습니다.

장시간 파이프라인 실패의 DLT 보존과 지연 재접수

안정성 · 2026.07

배경분석 하나가 수십 초 걸립니다. 실패하면 1초, 2초, 4초 뒤에 다시 시도하는데, 같은 이유로 또 실패하고 비용만 들었습니다.

수행파이프라인 실패는 바로 DLT로 보내고, 스케줄러가 60분 지난 메시지를 꺼내 retryCount를 올려 원래 토픽에 다시 넣습니다. offset은 그 뒤에 커밋합니다.

성과실패를 잃어버리지 않고 나중에 다시 처리합니다. retryCount가 올라가는 건 테스트로 확인했습니다.

한계재발행 뒤 커밋 전에 죽으면 중복이 생길 수 있습니다. at-least-once입니다. 그래서 exactly-once라고 말하지 않습니다.

인증·SSO·테넌트 경계

보안 · 2026.07 ~ 09

배경API가 permit-all이었습니다. 대시보드에서는 Axios 요청과 SSE가 동시에 401을 받으면 회전형 refresh token을 둘이 같이 써서 한쪽이 무효가 됐습니다.

수행JWT 필터를 넣고 ADMIN, OPERATOR, VIEWER 경로 규칙을 만들었습니다. 토큰 갱신은 공유 Promise 하나로 묶었습니다. A10 SSO는 Redis에 10분짜리 nonce를 두고 cookie state를 상수 시간으로 비교한 뒤 한 번만 소비합니다. 사용자 키도 (group_seq, login_id) 복합 키로 바꿨습니다.

성과토큰이 없으면 401, VIEWER가 ADMIN 경로를 치면 403, OPERATOR가 실행하면 200. 테스트로 고정했습니다.

한계운영 SSO 로그인이 실제로 됐는지, 키 관리와 침투 테스트는 이 커밋으로 말할 수 없습니다.

메일 도메인 구축 자동화

업무 자동화 · 2026.08

배경메일 도메인 구축 요청은 계속 들어오는데 사람이 처리하다 빠뜨리는 일이 있었습니다. 그렇다고 외부 시스템에 쓰는 작업을 무조건 자동으로 돌리는 건 위험했습니다.

수행접수, 승인 대기, 예약, 사전 점검, 등록, 그리고 완료, 취소, 수동검토, 실패 상태를 만들었습니다. webhook에 찍힌 사람을 믿지 않고 Jira를 다시 조회해 실제 담당자인지 확인합니다. 예약 시점에 이슈가 바뀌었는지도 다시 봅니다. 보상 삭제가 실패하면 사람 검토로 넘깁니다.

성과접수부터 등록, 보상까지 한 커밋(90개 파일)으로 관통했습니다. 그 뒤로 중복 라우팅, rollback, rate limit을 손봤습니다.

한계등록 성공률과 처리량은 아직 숫자로 없습니다.

성과표준 헤더를 존중하는 메일 서버 사이에서는 핑퐁이 멈춥니다. 멀티테넌트 라우팅이 한곳에 모였고, 복호화가 스레드마다 따로 돕니다.

한계모든 외부 메일 서버가 헤더를 존중하는 건 아닙니다. 동시성 재현 테스트는 커밋에 없습니다.
